## Module 1 — Notices & announcements: DONE, tested
- **Collections:**
  - `notices {school_id, title, body (sanitised plain text), category, priority, audience{scope school|classes|sections, class_names, section_ids}, attachments, requires_ack, status draft|review|scheduled|published|archived|cancelled, publish_at, expires_at (UTC; input interpreted as IST), revisions[], status_history[]}`
  - `notice_receipts {notice_id, user_id, read_at, ack_at}`, unique per notice + user.
- **Status changes:** scheduled notices publish at their set time, and published notices archive when they expire. Both changes run when notices are next fetched; there is no background worker. Editing a published notice requires a reason and saves a revision.
- **Read vs acknowledged:** opening a notice counts as read. Acknowledging is a separate, explicit tap.
- **Stats:** the denominator is verified guardian accounts with an active parent membership and an active child in the audience.
- **API:** `/api/notices` (CRUD, actions, attachments), `/api/parent/notices` (+ `/read`, `/ack`).
- **Attachments:** governed by document-level rules in `file_access.py` (purpose `notice`).
- **Permission:** a new `notices.manage` permission for owner, principal and school_admin.
- **Tests:** `tests/test_m3_notices.py` (2); testing agent iteration_14 PASS.

## Module 2 — Parent–teacher messaging: DONE, tested
- **Collections:**
  - `conversations {school_id, student_id, guardian_user_id, teacher_id, teacher_user_id, topic, status open|closed|escalated, follow_up, unread{parent,teacher}, reports[]}`
  - `messages {conversation_id, sender_user_id, sender_role, body, attachments, client_id (unique per conversation → idempotent), read_at, status}`
  - `message_templates`
- **Access:** checked against current data on every request. A parent needs a verified guardian link to the child. A teacher needs a current assignment to the child's section. Owner, principal and school admin can see a conversation only once it is escalated. Anyone else gets a 404.
- **Limits and pagination:** at most 20 messages per user per 10 minutes. Long threads load older messages by cursor (`?before=`).
- **Updates:** the app polls, every 5 s in an open thread and every 15 s on the conversation list. There is no real-time socket.
- **Office access (updated in Module 3):** owner, principal and school admin can only read escalated conversations. The compose box is hidden for them, and the API returns 403 if they try to post.
- **Not done yet:**
  - The school hours shown to parents are guidance only; messages are not blocked outside those hours.
  - Retention purge is not implemented.
  - The app has no attachment picker in the compose box yet. The API supports attachments.
- **Tests:** `tests/test_m3_messaging.py` (2); testing agent iteration_15 PASS.

## Module 3 — School events & calendar: DONE, tested
- **Collection:** `events {school_id, title, description, category, start_date, end_date (IST dates), start_time, end_time (HH:MM IST), location, audience, status draft|published|cancelled, cancel_reason, status_history}`
- **Feed:** a single `/api/calendar?start&end[&student_id]` feed returns events, exam schedules (from `exams`) and PTM dates (Module 4), scoped by role:
  - Managers see everything, including drafts.
  - Teachers see items for their own sections.
  - Parents see items for their children's sections, with an optional per-child filter.
  - Other staff see published items only.
- **Cancellation:** cancelling a published event requires a reason, and the event stays visible to families as "Cancelled".
- **Other endpoints:** `/api/calendar/upcoming` for home screen rows. Editing goes through `PATCH /api/events/{id}`.
- **Date/time pickers (Module 4 Part A):**
  - Native `@react-native-community/datetimepicker`: Android dialog, iOS inline/spinner in a sheet.
  - Expo Web: a month-grid sheet for dates, and 15-minute time chips plus a validated typed HH:MM fallback for times.
  - Dates and times are shown in human-readable form; the backend receives `YYYY-MM-DD` / `HH:MM` IST wall-clock values.
  - Client-side checks match the server: end date on or after start date, and end time after start time on the same day.
  - The edit sheet is prefilled from the existing event.

## Module 4 — PTM booking engine: DONE, tested
- **Collections:**
  - `ptm_sessions`: settings, policies, status draft|published|cancelled, history.
  - `ptm_slots`: generated by the server on publish; unique on (session_id, teacher_id, start_at); `booked` / `capacity` counters; status available|blocked|block_requested|cancelled.
  - `ptm_bookings`: school/session/slot/teacher/student/guardian IDs; start/end times (UTC + IST labels); status pending|confirmed|completed|no_show|cancelled_parent|cancelled_school|failed; reschedules[]; history[] with actor; shared/private notes.
  - `ptm_quotas`: per-child and per-guardian limits.
  - `ptm_unavailability` and `ptm_followups`.
  - `notifications`: durable in-app records with a dedupe index.
- **Concurrency safety:**
  1. The idempotency key is claimed by inserting the booking with unique (guardian_user_id, client_id).
  2. Per-child and per-guardian quotas use a conditional `$inc` with upsert and a unique key.
  3. A seat is taken with `find_one_and_update` on `status: available` and `booked < capacity`.
  4. The booking goes live under partial unique indexes: one live meeting per child per teacher per session, and one per guardian per start time.
  - Every step releases what it acquired if a later step fails.
  - Reschedule takes the new seat first and then moves the booking with a conditional update, so the old booking is kept if anything fails.
  - Cancelling a session flips its slots before its bookings. The booking path re-checks its slot after insert, so no confirmed booking can survive a cancelled session.
- **Conflicts:** checked on publish:
  - School holidays (published school-wide holiday events) block publishing.
  - A teacher's approved leave, explicit unavailability, and overlapping slots in another PTM block the affected slots.
  - Empty timetable periods are not treated as free.
- **Teachers:**
  - See their schedule and their slots (with child and guardian).
  - Can block slots (needs approval if the session requires it).
  - Record completed/no-show only after the start time.
  - Write shared and private notes; private notes are never sent to parents.
  - Add follow-ups, optionally shared with the guardian.
  - Revoking a teacher's assignment removes their access immediately.
- **Admin overrides:** require a reason and are audited.
- **Insights:** `/api/ptm/insights` returns figures computed from the database, filterable by date range, class, section and teacher. Definitions are included in the response.
- **Reminders:** in-app only, generated idempotently when the parent next opens the app (24 hours before the meeting). No push, SMS or WhatsApp delivery is implemented.
- **Screens:**
  - `/ptm`: role-aware; admin insights and sessions, teacher schedule, parent bookings and history.
  - `/ptm/new`: admin create form.
  - `/ptm/[id]`: admin management, teacher slots, or the parent booking flow child → teacher → slot → confirm.
  - `/ptm/booking/[id]`: booking detail.
  - Entry rows on staff, teacher and parent home screens, plus a calendar deep link.
- **Tests:** `test_m3_ptm.py` (6, including a real 6-way concurrent last-slot test, a capacity-2 slot, and 5-way identical retries) and `test_m3_ptm_edges.py` (7).

## Module 4 reliability fix — publishing: DONE, tested
- **Problem:** `_publish()` used to swallow every exception during slot insertion. It now publishes in two phases:
  1. The session moves from `draft` to `publishing`, which is not visible to parents or teachers and cannot be booked.
  2. Every expected slot is inserted. Retries are idempotent thanks to the unique (session_id, teacher_id, start_at) index. Only duplicate-key write errors are tolerated; any other database error propagates, and the session stays `publishing` with `publish_error` and a `publish_failed` history entry.
  3. The server checks that every expected slot exists. A missing slot, even after a silent short write, returns 503.
  4. Conflict blocking runs.
  5. The session moves from `publishing` to `published` with `slot_count`.
- **Retries and races:**
  - Retrying with `POST /ptm/sessions/{id}/publish` recovers.
  - Concurrent publishes produce exactly one set of slots.
  - Cancelling during an incomplete publish works.
  - The admin UI shows a "Publishing incomplete" state with a "Retry publishing" button.
- **Tests:** `tests/test_m3_ptm_publish_faults.py` (5). These run `_publish` in-process against real MongoDB with a wrapped collection and cover:
  - a mid-insert `AutoReconnect` after partial writes;
  - a silent short write;
  - a duplicate retry of a published session;
  - 4 concurrent publishes;
  - cancelling while incomplete.
- **Invalid event times:**
  - Jest UI tests (`__tests__/event-form*.test.tsx`) confirm that an end time before the start time disables Save draft, Publish and Save changes, and that fixing it re-enables them.
  - The Playwright web check (`frontend/e2e/event_time_validation.py`) passed in the preview.
  - The edit test exposed a stale-state risk with asynchronous native pickers. All picker setters now use functional state updates.
- **Accessibility:** `Button` now exposes `accessibilityState.disabled`.
